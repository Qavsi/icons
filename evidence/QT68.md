# Qt 6.8 compatibility verification

Verified on 2026-11-08. Linux: Debian 13, Qt 6.8.2, amd64
`tvm-builder:latest` under emulation on an arm64 Mac. Native: Qt 6.12.0
at `/Users/techalp/Qt/6.12.0/macos`. All rendering checks use software/offscreen.

## Root causes

### Offscreen backing-store alpha: seven assertions

The 6.8.2 diagnostic run returned `QImage::Format_RGB32`,
`hasAlphaChannel() == false`, with an opaque black corner. Counting alpha
therefore counts the whole 80x80 window, including when an icon is empty,
transparent, zero-sized or non-finite. FILL changes visible pixels, but its
alpha coverage cannot increase in an entirely opaque image.

This accounts for these unchanged assertions:

- `empty AppIcon is Null and paints nothing`
- `transparent caller color remains transparent`
- `native source fallback preserves transparent tint`
- `FILL1 changes the actual settings glyph geometry`
- `FILL changes star glyph pixels without choosing another asset`
- `zero-size Material glyph paints no ink`
- `non-finite Material size paints no ink and does not assign an invalid font pixel size`

Qt fixed backing-store alpha in
[QTBUG-136755 / qtbase 97f7819](https://github.com/qt/qtbase/commit/97f7819f1d9a2f97e61e50defc93c466bcc7cfe6).
The fix is present in 6.12.0 and absent in the tested 6.8.2/6.8.3 versions.
Requesting a window alpha buffer alone cannot fix the old offscreen plugin,
which selects its image format from the screen rather than the window.

The only test change is the capture helper: wait for exposure and use
`contentItem()->grabToImage()`. This renders the actual Qt Quick scene into
an image with alpha, including DPR, through the public
[QQuickItem API](https://doc.qt.io/qt-6.8/qquickitem.html#grabToImage).
The library's contract does not require alpha support from the platform
window backing store. No assertion or threshold was weakened.

### Static plugin initialization in a second engine: one assertion

Qt 6.8's plugin importer caches a static plugin under the module URI. In
another engine its dynamic-plugin path accepts that cached entry without
a `QPluginLoader`, then skips the static-plugin lookup and `initializeEngine`.
The second registry consequently lacks `material`; processing pending events
does not repair it. Shared plugins initialize both engines correctly.

Qt fixed this in
[QTBUG-140220 / qtdeclarative d66cfa9](https://github.com/qt/qtdeclarative/commit/d66cfa93eefa185aa15d42e9dc38cbcdbd0578cb),
backported to 6.10.1 and included in 6.12.0.

For static builds on Qt < 6.10.1, the library keeps the generated plugin
qmldir at a versioned resource location. The ordinary qmldir forwards to
that exact version. The versioned path makes the old importer select the
static instance and run its normal initialization in every importing engine.
Both files derive from Qt's generated metadata; the QML version and renderer
URL stay unchanged. `qt_query_qml_module` supplies the actual output path,
including a caller's custom `QT_QML_OUTPUT_DIRECTORY`. Resource targets flow
through the existing installation/export mechanism. No global QObject registry,
private Qt API, application changes or new dependency is needed.

The existing second-engine, engine-isolation and late-import assertions are
unchanged. Locally the original static build failed eight assertions per DPR;
the original shared build failed seven, with second-engine initialization
already passing.

### Fonts were packaged and registered

Before changing rendering, runtime diagnostics confirmed:

| Resource | Bytes | Valid QRawFont | Supports settings U+E8B8 |
| --- | ---: | --- | --- |
| MaterialSymbolsRounded.ttf | 15235612 | yes | yes |
| MaterialSymbolsRoundedOutline.ttf | 1667036 | yes | yes |
| MaterialSymbolsRoundedFilled.ttf | 1608044 | yes | yes |

`MaterialSymbols.ready` was true, `glyphCount` was 4304, and all three font
families were registered. The `material:settings icon unavailable` warning
comes from the deliberate request made before the Material import, while
the explicit source fallback is active. It is not evidence of missing fonts.

## Container preparation

The source is copied from the read-only mount, excluding host build products
and `.git`; the image is never rebuilt or committed:

```sh
rtk docker run -d --name qavsi-icons-qt68-fix --platform linux/amd64 \
  --entrypoint bash -v "$PWD":/src:ro tvm-builder:latest -lc \
  'mkdir -p /tmp/w && tar -C /src --exclude=./build --exclude=./.git -cf - . | tar -C /tmp/w -xf - && exec tail -f /dev/null'
```

The image also lacks `ensurepip`. Initial `python3 -m venv` and the
`font-error-missing_fonttools` fixture failed for that environmental reason.
Only the disposable container received the missing venv package:

```sh
rtk docker exec -u root qavsi-icons-qt68-fix bash -lc \
  'apt-get update && apt-get install -y --no-install-recommends python3-venv'
```

Result: exit 0. The positive fontTools environment is `/tmp/venv`, with
fontTools 4.68.0. It was initially bootstrapped with `venv --without-pip`
and `get-pip.py`; after the venv package is installed it can be reproduced by:

```sh
rtk docker exec qavsi-icons-qt68-fix bash -lc \
  'python3 -m venv /tmp/venv && /tmp/venv/bin/pip install fonttools==4.68.0'
```

The native tests use the existing `build/font-tools/bin/python`, fontTools
4.60.1. No fontTools or Python package was added to the library.
